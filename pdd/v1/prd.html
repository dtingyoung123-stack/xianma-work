拼多多物流工单处理 Agent V1.0 PRD · 评审版

1. 产品概述

1.1 项目背景

当前拼多多工单主要由客服人工根据 SOP 查询订单、物流、仓库、快递对接结果后，在拼多多工单后台选择处理项、发送话术、上传凭证并完结。物流类工单处理频次高，且大量动作具备明确 SOP：查询订单/物流、判断轨迹状态、对接快递/仓库、提交处理选项、上传凭证、跟进补发或退款。

本项目 V1.0 目标是在已确认 SOP 范围内建设一个物流工单处理 Agent，让 Agent 像真人客服一样自动操作拼多多工单/订单后台，并结合 OMS、TMS、金山文档等信息源完成可自动化的判断和处理；无法自动处理、规则缺失、系统不可访问或命中高风险时，推送钉钉人工接管。

1.2 V1.0 目标

  1. 支持 7 个物流类型工单场景的自动识别、自动处理和异常转人工。
  2. 对规则明确、数据可读取、凭证满足要求的工单，优先由 Agent 自动处理到完结。
  3. 对规则缺失、超权限、系统不可达、数据不完整、微信群对接、紧急/临近超时等场景，推送钉钉人工接管。
  4. 建立最小数据看板，支持试点验收、过程监控、转人工追踪和单工单日志追溯。
  5. 保留完整操作日志，用于复盘、追责、规则优化和技术排障。

1.3 V1.0 范围

1.3.1 本期做什么

本期只处理以下 7 个物流类型场景：

序号 物流场景 V1 处理目标
1 消费者担忧货物无法送达（催促/咨询物流） 判断物流正常/48h 内未更新/超 48h 未更新，按 SOP 催件、记丢件、补发或完结
2 消费者反馈未收到货 查询签收/送达信息，对接签收未收到，提交送达地址、自取地址或兜底转人工
3 物流轨迹已退回，消费者咨询物流问题 告知退回/异常，按买家诉求协商退款或补发，平台协助后按规则处理
4 派件阶段物流断更 对接快递催件，选择继续派送和预计送达日期，后续更新后完结
5 消费者未收到货 · 处理情况跟进 读取聊天记录，按已收到/未收到分支处理，必要时对接丢件并跟进退款/补发
6 召回 / 物流在途退款工单 判断待揽收、未离开发货地、在途、派件、代收点等状态，按拦截/拒收/召回/退款规则处理；关联规则见 5.6
7 物流异常，消费者要求补寄 判断物流是否恢复，未恢复时拦截原单、创建补发单并填写补发单号；关联规则见 5.6

1.3.2 本期不做什么

不做范围 说明
售后类型工单 如少发、质量问题、承诺补寄、投诉紧急工单等，V1 不纳入自动处理
催发货类型工单 如普通催发货、导单断更、异常网点预警、好人好事工单等，V1 不纳入自动处理
售中类型工单 如改地址、已签收改地址等，V1 不纳入自动处理
非上述 7 个场景的退款/售后物流相关工单 即使涉及物流动作，也不在 V1 范围内
微信群自动化 微信群不做自动读取和自动发送；命中微信群对接分支时转钉钉人工
复杂数据分析 不做趋势分析、店铺对比、人效测算、SOP 缺口自动分析、复盘报告
复杂权限后台 V1 不建设完整权限配置后台，先按固定规则和人工确认项执行
全量店铺覆盖 先按试点店铺运行，不直接覆盖全部店铺

1.4 核心原则

  1. 能 Agent 自动处理的，不为了简化 MVP 而强制转人工。
  2. Agent 只按已确认 SOP、权限规则和可读取数据执行。
  3. 未确认规则、判断冲突、关键字段缺失、系统异常、超权限、高风险或微信群对接，统一转钉钉人工。
  4. 补发、退款可以由 Agent 自动执行，但必须满足规则、权限、凭证和数据完整性要求。
  5. 全流程留痕：查询数据、判断依据、执行动作、话术、凭证、状态、失败原因、转人工原因均需记录。

2. 用户角色与使用场景

角色 使用场景 关注点
客服人员 接收 Agent 无法处理或需人工确认的工单 接管摘要清晰、知道 Agent 已做什么、下一步怎么处理
客服主管 / 业务负责人 评审规则、查看处理质量、确认转人工原因 自动处理是否符合 SOP、是否有资损风险、是否可追溯
技术 / 开发 评估系统对接、自动操作、异常处理和日志字段 字段来源、系统边界、状态流转、失败重试、权限控制
运营 / 管理者 查看试点处理量、成功率、失败率、人工接管情况 看板指标是否支撑试点评估

3. 整体流程图

4. 功能模块

4.1 Agent 处理能力

模块 功能说明
工单识别 识别是否属于 V1 物流 7 场景；非范围工单跳过，不进入 Agent 自动处理和钉钉转人工
数据读取 读取拼多多工单/订单后台、OMS、物流轨迹、TMS、金山文档等必要信息
规则判断 按 SOP 判断物流状态、48h 断更、预计送达日期、仓库渠道、低值品/拦截品、退款/补发边界
自动操作 自动点击工单选项、发送话术（优先使用系统统一回复；统一回复不符合 SOP 或无统一回复时，按 SOP 自行输入话术文本）、上传凭证、创建补发、填写补发单号、同意退款等
外部对接 自动对接 TMS；金山文档视技术可行性自动读写；微信群不自动化
任务队列 拉取待处理工单，识别并跳过非 V1 范围工单；V1 范围内工单按倒计时和紧急程度处理
转人工 对无法自动完成的工单生成接管摘要，通过钉钉推送到单独对接群（B02 已确认）
运行监控与失败重试 系统异常可重试，最多重试 3 次，重试失败转人工，并记录失败原因和重试次数
基准数据管理 使用地址表、权限表作为判断依据；版本过期、格式异常、字段缺失时转人工
日志留痕 记录所有读取、判断、操作、失败、转人工和人工接管信息

4.2 数据看板

V1 看板只做试点上线必需能力：

  1. 全局范围控制：顶部选择时间范围、店铺范围后点击查询，决定整页统计口径；V1 不放顶部状态筛选。
  2. 当前范围汇总：展示当前筛选范围内的工单总量、非物流类工单数、今日处理数、累计处理数、自动成功数、转人工数、处理失败数、Agent 平均响应时长、响应时长缩短比。
  3. 场景汇总：按 7 个物流场景展示当前范围内的总数、自动成功数、转人工数、失败/异常数。
  4. 工单明细：按工单维度展示店铺、订单、运单、场景、处理状态、结果、转人工原因等。
  5. 工单详情：展示 Agent 判断依据、执行动作、话术、凭证、失败/转人工原因和操作日志。
  6. 明细查询：按工单号、订单号、运单号、子场景、是否转人工、失败/转人工原因查询明细。
  7. 导出：导出当前查询范围内的工单明细，V1 不导出汇总统计。
  8. 试点健康度：展示应自动处理成功率、应转人工正确率、转人工原因完整率、日志完整率等辅助观察项。
  9. UI 要求：布局简洁、大气、高级，信息密度适中，优先保证评审和试点监控可读性。

5. Agent 功能详细说明

5.1 物流工单自动处理能力

功能描述：
Agent 自动识别 V1 范围内的物流工单，读取拼多多后台、OMS、物流轨迹和外部对接结果，按已确认 SOP 自动选择处理项、发送话术、上传凭证、创建补发/同意退款；无法自动处理时转钉钉人工。

触发条件：

  1. 新工单进入拼多多工单后台。
  2. 工单类型命中 V1 物流 7 场景。
  3. 店铺属于试点店铺范围。
  4. Agent 账号具备读取和操作权限。

输入数据：

数据类型 关键字段/信息 来源
工单信息 工单编号、店铺、工单类型、子场景、倒计时、平台可选项、工单要求 拼多多工单后台
订单信息 订单号、订单状态、买家信息、商品、实付金额 拼多多订单后台 / OMS
物流信息 运单号、快递公司、轨迹节点、最近轨迹时间、签收/退回/派送/代收点状态 拼多多后台 / OMS / 快递轨迹
仓库信息 发货仓库、仓库类型、仓库发货地址、对接渠道 OMS / 代发仓发货地址.xlsx / SOP
权限信息 低值品/拦截品标识、补偿/退款权限、高风险阈值 OMS / 拼多多权限表0617.xlsx
外部对接信息 TMS 处理结果、金山文档回复、凭证截图 TMS / 金山文档

处理逻辑：

  1. 判断是否为 V1 范围内 7 个物流场景；非范围工单直接跳过，保留原人工流程处理。
  2. 对 V1 范围内工单读取工单、订单、物流、OMS 数据。
  3. 判断是否紧急、是否剩余 1 小时内临近超时；若是，转钉钉人工。
  4. 按场景规则判断下一步动作。
  5. 若需外部对接：
    • 筑越仓：走 TMS 系统/客服物流对接表单。
    • 金山文档渠道：技术确认可读写后自动提交和读取。
    • 微信群渠道：V1 不自动化，转钉钉人工。
  6. 满足自动处理条件时，Agent 自动执行后台操作：发送话术时优先匹配系统统一回复；统一回复不符合当前场景 SOP 或无统一回复时，Agent 按 SOP 自行输入话术文本。
  7. 执行完成后记录日志并更新看板。

自动处理边界：

  1. 规则明确。
  2. 数据完整。
  3. 系统可访问。
  4. 操作项在 Agent 授权范围内。
  5. 外部对接结果可读取且结果明确。
  6. 补发/退款满足 SOP、凭证和权限要求。

转人工条件：

转人工只适用于已识别为 V1 物流 7 场景、但 Agent 无法继续自动处理的工单。

  1. 紧急工单或剩余 1 小时内临近超时工单。
  2. 关键字段缺失，如订单号、运单号、发货仓库、物流轨迹缺失。
  3. 拼多多后台、OMS、TMS、金山文档不可访问。
  4. 金山文档技术不可读取/写入，且该分支依赖文档结果。
  5. 命中微信群对接渠道。
  6. 买家表达不明确、无明确同意退款/补发、聊天语义无法判断。
  7. 超出权限、责任边界未确认、涉及高风险资损。
  8. Agent 操作失败且重试 3 次后仍失败。

输出结果：

  1. 工单自动处理成功。
  2. 工单处理失败并记录原因。
  3. 工单转钉钉人工接管并附接管摘要。
  4. 非 V1 范围工单已跳过，不进入看板核心指标。
  5. 看板与操作日志同步更新。

5.2 七个物流场景处理规则

场景 触发条件 Agent 必读数据 自动处理动作 转人工条件 输出结果
消费者担忧货物无法送达 工单诉求为催促/咨询物流，担忧无法送达 最近物流轨迹、最近轨迹时间、订单号、运单号、发货仓库、仓库渠道 物流正常更新时选择“物流已正常更新”；48h 内未更新时对接催件，选择“需联系物流核实”并延后轨迹更新日期 2 天；超 48h 未更新时对接记丢件并进入补发流程 无轨迹、48h 起算点无法判断、需微信群对接、补发所需仓库/库存/单号无法获取 完结、跟进、补发成功或转人工
消费者反馈未收到货 买家反馈签收后未收到或未收到货 签收状态、送达地址、电话、物流轨迹、仓库渠道、对接凭证 对接“签收未收到”，填写送达地址和电话，上传凭证；可自取时填写自取地址；无自取选项时选择可送到指定地址 对接结果不明确、凭证无法获取、微信群对接、地址/电话缺失 提交承诺核实、完结或转人工
物流轨迹已退回 物流轨迹显示退回/异常，买家咨询 退回轨迹、买家诉求、聊天记录、是否申请退款、补发条件 留言告知退回/异常并协商；买家同意补发时创建补发单并填写单号；买家同意退款时选择协商一致已退款并上传聊天记录；平台代申请退款后可同意 买家无明确诉求、聊天记录无法判断、补发/退款条件不满足 补发、退款、平台协助或转人工
派件阶段物流断更 物流处于派件阶段但长时间未更新 派件轨迹、最近轨迹时间、发货仓库、可选预计送达日期 对接快递催件，选择“与消费者协商一致继续派送”，预计送达日期最多延后三天，物流更新后选择正常更新完结 预计日期不可选、对接结果不明确、剩余 1 小时临近超时 跟进派送、完结或转人工
消费者未收到货 · 处理情况跟进 已有未收到货相关处理，需跟进结果 聊天记录、买家是否反馈已收到、物流状态、仓库渠道 买家反馈已收到时上传聊天记录并确认拿到快递；买家反馈未收到时对接丢件，留言协商退款/补发，买家回复后选择对应结果 聊天语义不明确、买家未回复、需微信群对接、补发/退款条件不满足 确认收到、协商退款/补发或转人工
召回 / 物流在途退款工单 买家申请退款或平台要求召回/拦截/拒收 物流阶段、是否未离开发货地、是否到达买家当地、发货仓库、低值品/拦截品标识、拦截/拒收凭证 待揽收/未离开发货地时拦截成功后退款；在途时核实低值品/拦截品，符合规则或未出当地且拦截成功可退款；派件/代收点时拒收成功后退款，否则跟进召回 无成功凭证、非低值品且拦截/拒收失败、当地判断缺失、超权限/高风险 退款成功、召回跟进或转人工
物流异常，消费者要求补寄 买家要求补寄且物流异常 物流是否恢复、原单轨迹、仓库渠道、库存/补发条件、补发单号 物流已恢复时选择“物流轨迹已恢复更新”；未恢复时原单物流对接拦截，OMS 创建补发单，手工配货并填写补发单号 无库存、补发单创建失败、原单拦截结果不明确、需微信群对接 物流恢复完结、补发成功或转人工

5.3 外部对接能力

对接对象 V1 自动化要求 备注
拼多多工单/订单后台 必须自动读取和自动操作 Agent 需像真人客服一样完成查询、点击、提交、发送话术、上传凭证

5.6 低值品/拦截品规则

  1. 以 OMS 是否标记“低值品/拦截品”为统一判断依据。
  2. 筑越仓低值品：在 TMS 登记弃件处理后，可按规则处理仅退款。
  3. 代发仓低值品/拦截品：按 OMS 标识对接拦截/拒收后处理退款。
  4. 普通拦截/拒收场景：原则上需拿到拦截成功或拒收成功凭证后再退款。
  5. 非低值品若物流未出当地且已拿到拦截成功凭证，可直接退款。

6. 数据看板功能详细说明

6.1 数据概览

功能描述：同一个看板页面内，先通过顶部筛选确定查看范围，再展示该范围下的数据。默认查看“全部已接入店铺”，V1 阶段即全部试点店铺；选择单个店铺后，汇总指标、场景汇总和工单明细同步切换到该店铺。
目标用户：客服主管、业务负责人、技术、运营。
展示指标：

指标 含义 数据来源
今日处理工单数 今日进入 Agent 且属于 V1 物流 7 场景的工单数，包含待重试、处理中、等待外部结果、处理成功、处理失败、已转人工；不包含待处理和已跳过工单 Agent 日志
累计处理工单数 自 V1 试点开始日起，累计进入 Agent 且属于 V1 物流 7 场景的工单数；不包含已跳过工单 Agent 日志
自动处理成功数 Agent 自动完成并提交成功的工单数 Agent 状态
转人工数 Agent 推送钉钉人工接管的工单数 Agent 状态 / 钉钉推送记录
处理失败数 Agent 操作失败且最终仍停留在失败状态的工单数；重试失败后已成功转人工的工单不双算，只计入转人工数，不计入处理失败数 Agent 日志
Agent 平均响应时长 自动成功工单从工单进入 Agent 队列到 Agent 开始处理的平均时长（响应速度） 工单进入队列时间 / Agent 开始处理时间
响应时长缩短比 相比人工基准响应时长（30～60 分钟，业务口径，依据不足仅供参考）的缩短比例 Agent 日志 + 人工基准响应时长
工单总量 当前筛选范围内 Agent 扫描到的全部工单数，含 V1 物流范围和非物流类跳过工单；等于 V1 物流工单数 + 非物流类工单数 Agent 日志（含跳过记录）
非物流类工单数 当前筛选范围内，Agent 识别为非 V1 范围并跳过的工单数；不进入自动成功率、转人工率等核心指标分母 Agent 跳过日志

顶部范围控制：时间范围、店铺范围、查询按钮。店铺默认“全部已接入店铺”；V1 中“全部已接入店铺”等同于全部试点店铺，不代表全部 80 家历史店铺。用户选完时间和店铺后点击“查询”，整页汇总、场景和明细按当前条件刷新。
明细查询条件：工单号、订单号、运单号、物流子场景、是否转人工、失败/转人工原因。明细查询只影响工单明细列表，不反向改变上方汇总指标和场景汇总口径。
刷新规则：看板数据建议每 5 分钟自动刷新；单工单处理状态在 Agent 完成、失败、转人工后目标 1 分钟内可见；支持手动刷新；最终口径由技术评审确认。
异常状态：看板顶部展示同步提示条，仅在出现异常时提示。提示内容包括：日志延迟、钉钉推送回执待同步、数据同步失败、看板刷新失败。其触发规则如下：

  1. 失败类异常 一旦发生立即提示。
  2. 延迟类异常 超过 1 个刷新周期仍未同步时提示，V1 刷新周期按 5 分钟计算。
  3. 提示条展示于顶部全局筛选下方，作为常驻告警区域；无异常时不占位。
  4. 异常恢复后，下一次自动刷新或手动刷新时自动消失，V1 不做人工确认关闭。
  5. 提示文案以简短汇总为主，例如“同步提示：当前存在 2 条日志延迟、1 条钉钉推送回执待同步。” 价值指标说明：响应时长缩短比用于判断 Agent 是否产生实际响应效率价值，V1 需在看板展示。人工基准响应时长（工单生成到人工开始处理）为 30～60 分钟（业务口径，依据不足仅供参考）。

6.1.1 导出规则

导出用于评审复盘和试点分析，V1 默认只导出当前查询范围内的工单明细，不导出汇总统计，不做独立账号权限管理。

  1. 导出对象：当前查询范围内可见的工单明细。
  2. 导出内容：工单编号、店铺名称、订单号、运单号、物流子场景、Agent 状态、处理结果、是否转人工、转人工/失败原因、开始处理时间、完成时间、处理耗时、备注。
  3. 导出结果：用于复盘、汇报、问题排查；不改变当前页面筛选和统计口径。
  4. 权限说明：V1 默认仅内部项目相关人员使用，不做独立账号和权限管理；后续如开放给更多角色，再补充权限控制。

Agent 状态与处理结果区分：

  1. Agent 状态 表示系统流程状态，例如待处理、处理中、等待外部结果、处理成功、处理失败、已转人工、已跳过、待重试。
  2. 处理结果 表示业务处理结论，例如完结、跟进、补发成功、退款成功、确认收到、转人工。
  3. 同一个 Agent 状态 可能对应不同 处理结果。例如 处理成功 可对应完结、补发成功、退款成功、确认收到；已转人工 的处理结果为转人工。

13.1 核心指标判定口径

应自动处理工单 和 应转人工工单 必须由 Agent 在执行关键动作前，基于当前已读取的数据和已确认 SOP 规则做出预判并写入日志，不能在处理完成后倒推归类。

指标口径 定义 判定时点
应自动处理工单 工单属于 V1 物流 7 场景，且规则明确、必需数据完整、未命中转人工条件，Agent 应继续自动处理 执行平台提交、退款、补发、上传凭证等关键动作前
应转人工工单 工单属于 V1 物流 7 场景，但命中规则不明确、关键字段缺失、超权限、微信群对接、系统不可达等转人工条件，Agent 应停止自动处理并推送人工 执行转人工推送前
非 V1 跳过工单 工单不属于 V1 物流 7 场景，Agent 跳过，不纳入核心看板指标和自动/转人工成功率分母 场景识别完成后

对应计算：

应自动处理工单中的实际自动成功率 = 应自动处理且最终自动处理成功的工单数 / 应自动处理工单数
应转人工工单中的正确转人工率 = 应转人工且实际已转人工的工单数 / 应转人工工单数

13.2 试点价值观察指标

响应时长缩短比用于衡量 Agent 相比人工的响应速度提升，V1 纳入看板展示，作为试点价值观察指标，不作为强验收指标。该指标按当前顶部筛选范围统计。

人工基准响应时长：30～60 分钟（工单生成到人工开始处理的等待时长；业务部门经验估算，依据不足，仅供参考）。

响应时长缩短比 = (人工基准响应时长 - Agent 平均响应时长) / 人工基准响应时长

口径说明：

  1. Agent 平均响应时长：自动成功工单从工单进入 Agent 队列到 Agent 开始处理的平均时长。
  2. 人工基准响应时长：30～60 分钟（工单生成到人工开始处理的等待时长，业务估算，依据不足仅供参考）。
  3. 看板展示单一估算值（以 60 分钟为基准计算），依据不足，仅供参考。
  4. 转人工工单不纳入 Agent 平均响应时长统计。
  5. 看板展示该指标时，需同时展示人工基准响应时长和 Agent 平均响应时长，便于业务理解计算依据。
  6. 如试点期间能采集到更精确的人工响应时长样本，可更新基准值。

功能性验收：

  1. Agent 能识别 V1 范围内 7 个物流场景。
  2. Agent 能识别非 V1 范围工单并跳过，不处理、不推送钉钉、不影响原人工处理流程。
  3. Agent 能读取拼多多后台、OMS、物流轨迹等必要数据。
  4. Agent 能按规则执行低风险和规则明确的自动处理动作。
  5. Agent 能在 TMS 自动提交/读取物流对接结果。
  6. 金山文档可行时，Agent 能自动提交/读取；不可行时能转人工并记录原因。
  7. 微信群对接分支不自动处理，能转人工。
  8. 处理失败或转人工时必须记录原因。
  9. 每个处理工单均可在看板查看详情和操作日志。
  10. 看板支持导出当前查询范围数据。
