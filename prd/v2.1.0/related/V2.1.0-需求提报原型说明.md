# 先马·AI Studio V2.1.0 需求提报原型说明

> 版本：V2.1.0  
> 原型基线：完整复制自 V2.0.0 交互原型后增量扩展  
> 状态：产品原型，供评审与后续增量 PRD 使用；不代表生产功能已开发、部署或上线

## 一、版本关系

- V2.0.0 基线内容已完整继承至本版本 `../prototype/`。
- V2.1.0 当前目录：本目录
- V2.1.0 保留 V2.0.0 的全部应用端、技能库、浏览器任务和管理后台页面。
- 本期只增量加入 AI Studio 自身产品需求的分析、提交、个人查看、后台查看与导出。

## 二、本期新增页面

### 应用端

1. `应用端/应用端_需求提报.html`
   - 独立需求分析对话；
   - 能力资料读取状态；
   - 动态单问题追问；
   - 阶段总结；
   - 最终摘要；
   - 建议解决方向；
   - AI提交建议；
   - 摘要确认与独立提交；
   - 已有能力直接解决、建议补充、暂不建议提交、坚持提交和提交失败分支；
   - 空白初始态：用户发送第一条需求后，系统自动启动能力核对、逐轮追问和右侧动态更新；
   - 本期只保留一条未提交草稿，支持暂存、自动恢复、继续补充和二次确认后放弃并新建；
   - 不提供用户手动切换分析阶段的状态下拉框。

2. `应用端/应用端_我的提报.html`
   - 属于需求提报模块子页面，不设置应用一级导航；
   - 仅从需求提报页右侧“查看我的提报”或提交完成入口进入；
   - 仅查看本人已提交记录；
   - 列表和只读结构化详情；
   - 已提交内容不可编辑，需要修改时重新发起。

### 管理后台

3. `管理后台/管理后台_需求管理.html`
   - 累计提交、本月新增、AI建议提交、坚持提交概况；
   - 搜索与筛选；
   - 全部已提交需求列表；
   - 正常提交与坚持提交区分；
   - 首次/重复导出演示。

4. `管理后台/管理后台_需求详情.html`
   - 原始诉求摘录；
   - 结构化需求分析；
   - 能力文档版本及现有能力对比；
   - 建议解决方向；
   - 范围、依赖、风险和验证方式；
   - AI判断、用户确认和提交授权；
   - 需求 ID 和导出记录。

## 三、导航变化

### 应用端

应用端一级导航固定为：

```text
新对话
搜索
技能库
提示词库
定时任务
────────
需求提报
```

“需求提报”位于一级导航末尾，通过分隔线与日常任务入口区分；账号菜单不重复提供需求提报。“我的提报”作为需求提报的子页面，不在左侧单独展示。需求提报和我的提报页面继续复用公共侧栏中的项目及普通 AI 对话列表，不提供需求提报对话历史列表。没有草稿时点击需求提报进入空白页；存在唯一草稿时自动恢复。一条需求只使用一段独立需求分析流程，不与普通 AI 对话混合。

### 管理后台

模块顶部导航变为：

```text
首页｜技能管理｜用户管理｜需求管理｜基础配置｜版本发布
```

需求管理为一级页面，不放入基础配置或技能管理二级页签。

## 四、关键业务边界

- 只收集先马·AI Studio 自身产品需求。
- 正式产品由 Agent 在分析前读取随版本部署的 `docs/AI_CAPABILITIES.md`；每次发布新版本时由发布流程自动从正式产品事实源生成或刷新快照，生成或校验失败阻断发布。资料异常时不能强判现有能力关系。当前静态原型不包含该文件，也不执行真实读取，仅用预设数据演示读取成功、异常或过期状态。
- 已有能力可直接解决时先引导员工使用，员工确认问题已解决后结束且不生成需求记录；仍有差距时再继续分析。
- AI 只有建议权，不能彻底拦截用户坚持提交。
- 需求理解、能力对比、建议方向、MVP范围、风险、验证方式和是否建议提交统一由需求分析 Skill 输出；技术层只做结构、枚举、状态、权限、版本、跨字段和幂等硬校验，不另做业务判断。
- `建议补充` 不进入普通提交；`暂不建议提交` 可填写理由坚持提交，也可选择暂不提交并保留为唯一草稿。
- 摘要确认不等于提交，必须有第二次独立确认提交动作。
- 本期最多保留一条未提交草稿，不建设未提交历史列表、搜索、归档或多草稿切换。切换到项目、普通对话或其他页面后自动保存；返回需求提报时恢复对话、当前追问、分析阶段和右侧需求理解，并继续原流程。
- 存在草稿时发起新需求，先选择继续当前需求或放弃并新建；放弃需二次确认，清除后不可恢复。现有能力已解决、范围外和主动放弃均不保留历史，也不进入我的提报或后台。
- 提交成功后由提交服务生成唯一需求 ID `REQ-YYYYMMDD-NNN`；应用端和管理后台展示同一 ID。
- Skill、前端和导出服务均不生成编号；导出只沿用提交时的需求 ID。
- 同一需求重复导出只更新首次/最近导出时间和导出次数，不更换需求 ID。
- 后台一期不做审核、负责人、优先级、排期、评论和开发状态流转。
- 提交内容和AI判断在后台只读。
- 员工端只展示“已提交”，后台单独维护“未导出/已导出”；导出不代表立项或排期。
- V2.1.0 只做单条 Markdown 导出，不做批量导出、合并文件或 ZIP 打包。
- 后台 MVP 列表只保留搜索和导出状态筛选，字段顺序为需求 ID、需求标题、提报人/部门、AI 判断/提交方式、提交时间、导出状态和操作；需求 ID 与标题分列，完整 ID 可精确查询，标题搜索仍保留。真实问题、能力关系等完整信息进入详情页。
- 静态原型使用浏览器本地存储演示导出次数和首次/最近导出时间的刷新留存；生产需求 ID 与导出记录必须由服务端持久化，并由提交服务保证 ID 唯一。
- 导出按钮必须生成并下载单条 Markdown 文件，导出中禁止重复点击；失败时保留原状态并提供重新导出。
- 后台需求查看与导出仅面向具有需求管理权限的管理员；本期不新增独立角色配置页面，由宿主管理后台承接权限控制。
- 当前 HTML 是静态原型，不接入真实模型或需求分析 Skill；正式产品由 Agent 层调用 Skill。原型只通过预设场景模拟关键状态，不得据此表述为 AI 能力已实现。

## 五、原型示例数据说明

应用端需求提报页面不再默认展示“新品 Excel 自动登记”示例，而是以空白新需求对话开始；用户发送内容后，原型用于验证自动能力核对、单问题追问、右侧需求理解动态更新、摘要确认与提交分离。

应用端原型使用隐藏 URL 参数验证关键分支：`?scenario=direct`、`?scenario=supplement`、`?scenario=not-recommended`、`?scenario=capability-error`、`?scenario=out-of-scope`、`?scenario=submit-error`。默认不显示调试控件，避免把评审入口带入员工正式界面。

空白需求页支持三个首条消息演示口令：`测试不提交` 经过完整追问后进入暂不建议分支，演示者选择暂不提交并形成唯一草稿；`测试提交` 经过完整追问后进入建议提交分支；`测试坚持提交` 经过完整追问后进入暂不建议分支，演示者选择坚持提交、填写理由并完成双重确认。口令必须作为第一条消息完全匹配，不直接跳过分析流程，也不代表正式产品按关键词决定 AI 判断。

“新品 Excel 自动登记”只保留在“我的提报”和管理后台，作为已提交记录的完整详情示例。另用“多店铺批量处理”和“暂不建议但提报人坚持提交”作为列表分支示例。全部数字、角色、能力版本和时间均为原型演示数据，不是生产事实。
