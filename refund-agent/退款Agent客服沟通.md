# 退款 Agent 客服沟通内容

编写人：梦蝶　编写日期：2026-07-07

沟通目标：确认客服现有退款 SOP、业务规则、平台操作方式和风险边界，为后续设计「跨平台退款处理 Agent」提供依据。

## 1. 当前背景

我们目前有 100 多家店铺，分布在拼多多、闲鱼、京东、淘宝、天猫等平台。

由于各平台 API 申请和店铺授权成本较高，现阶段更现实的方案是：让 Agent 通过浏览器进入各平台后台，模拟人工客服完成查询、判断、填写、提交和记录等操作。

因此，客服提供的 SOP 需要从「人能看懂」升级为「Agent 能照着执行」。

## 2. 希望客服提供的核心资料

### 2.1 退款 SOP

请客服提供当前退款处理 SOP，最好按平台和处理类型拆分。

这份 SOP 不只是操作步骤，也需要包含业务规则、上线标准、不能退款的边界、审批规则和异常处理。简单说：Agent 能不能处理、该怎么处理、什么时候必须停下来，都应该在 SOP 里写清楚。

每个 SOP 建议包含：

| 内容 | 需要说明什么 |
|---|---|
| 适用范围 | 适用平台、店铺、商品类型、订单状态 |
| 处理类型 | 仅退款、退货退款、部分退款、平台介入等 |
| 上线标准 | 哪些场景可以进入 1.0 自动退款，哪些只能转人工 |
| 触发条件 | 什么状态下需要客服处理 |
| 判断规则 | 什么情况同意、拒绝、协商、转人工 |
| 禁止退款 | 哪些商品、订单、用户、状态不能退款 |
| 审批规则 | 多少钱以内可处理，多少钱以上需主管/财务审批；审批人响应时效上限，超时按什么规则处理 |
| 时效要求 | 各平台、各售后类型的强制处理时效（如“XX 小时未处理自动退款”），以及是否已出现过因超时被平台自动判责的情况 |
| 唯一标识 | 售后单的唯一键定义（交易号 + 售后单号等），同一交易号是否可能存在多个售后单 |
| 操作步骤 | 进入哪个后台、点哪个按钮、填什么内容 |
| 所需信息 | 订单号、售后单号、金额、物流、凭证、聊天记录等 |
| 金额规则 | 全额退款、部分退款、运费、优惠券、积分如何处理 |
| 成功判定 | 区分“退款提交成功”和“退款到账成功”，Agent 处理到哪一步算完成 |
| 异常处理 | 找不到订单、金额异常、平台报错、登录失效、订单状态被买家撤回等怎么办 |
| 话术模板 | 回复买家的标准话术、平台备注模板 |
| 风控边界 | 哪些情况必须人工处理，哪些禁止自动操作 |

### 2.2 配套材料

除了 SOP 本身，也希望客服提供配套材料，用于校验 SOP 是否完整、是否能落地：

- 每个平台典型退款流程的操作录屏
- 关键页面截图：售后列表、售后详情、退款按钮、拒绝按钮、弹窗、失败提示
- 测试/只读子账号，用于我们进入后台查看真实页面和状态
- 安排客服同学陪跑 1-2 次，现场讲解真实案例
- 指定一位负责人对接 SOP、账号、陪跑和后续问题确认
- 最近一段时间的脱敏退款案例，包括自动退款、人工退款、拒绝退款、转人工、平台介入案例
- 各平台退款规则、平台处罚风险和特殊限制的原始资料或链接
- 说明退款使用的客服账号是共享给多个功能（例如与补发通知 Agent 共用同一批账号），还是单独一批，便于评估账号风控和登录状态的影响范围

调研阶段建议先提供只读权限，包括订单查询、售后查询、退款详情、物流、聊天记录查看等。等 SOP、低风险范围和审批边界确认后，再为试运行配置受限的退款操作权限。

## 3. 需要重点梳理的处理类型

我们建议先按以下统一类型梳理，后续再映射到各平台的具体名称。

| 统一类型 | 典型场景 | 1.0 建议 |
|---|---|---|
| 未发货仅退款 | 买家申请退款，订单还未发货 | 若平台/系统已自动退款，则不作为重点；只处理系统未自动处理的漏单 |
| 已发货但未揽收退款 | 已发货但物流未揽收、可拦截 | 规则明确时可作为 1.0 自动退款场景 |
| 已发货在途退款 | 货在途，买家要求退款但不退货 | 拦截成功或符合 SOP 时，可低风险自动处理 |
| 已收货仅退款 | 买家已签收但要求不退货退款 | 建议 1.0 转人工 |
| 退货退款 | 买家退货，商家收货后退款 | 退货签收/验收入库后，可自动确认退款 |
| 小额部分退款 | 差价、少件、破损补偿 | 金额标准明确时，可自动发起部分退款 |
| 平台介入/纠纷 | 投诉、仲裁、平台判责 | 1.0 不建议自动决策 |

## 4. 风险说明

退款 Agent 属于高风险操作，主要风险包括：

- 误退款：金额、订单、用户、商品判断错误
- 越权操作：Agent 操作了不该处理的店铺或订单
- 平台处罚：不符合平台规则导致店铺扣分、限制或纠纷升级；部分平台商家协议可能明确禁止“自动化工具操作店铺后台”，一旦被平台识别为异常操作，可能触发处罚，这属于经营风险而不只是技术风险
- 时效风险：各平台对售后单基本都有强制处理时效，商家超时未处理会被系统自动判买家赢（自动退款/自动介入），这是平台规则问题，Agent 的扫描频率必须比这个时效更紧，否则做了也没用
- 并发/重复风险：同一售后单可能被 Agent 和人工同时处理，若没有唯一键锁定机制，容易出现重复操作或双重退款
- 资金风险：高金额、重复退款、恶意退款未被识别；Agent 发起的退款金额与平台实际扣款是否一致，若缺少核对机制，容易出现资金差异且难以及时发现
- 纠错风险：退款一旦执行基本不可逆，一旦 Agent 判断错误已经把钱退了，若没有明确的补救流程（找买家要回、走平台申诉、内部核销），损失很难追回
- 隐私风险：订单、聊天记录、手机号、地址等信息泄露
- 页面变化风险：平台后台改版后，Agent 点错按钮或无法判断状态
- 登录风险：验证码、扫码、异地登录、账号风控导致流程中断；风控触发后处理动作可能卡在“退款未提交”的中间状态，需要明确这种中间态的处理方式

因此需要做到：

- 全量操作留痕：截图、日志、判断依据、操作结果
- 分级权限控制：只读、建议、待审批执行、自动执行
- 高风险强制转人工
- 真实退款权限逐步开放
- 首期不追求全自动覆盖所有退款场景
- 售后单唯一键去重和锁定，避免同一单被重复处理或双重退款
- 建立资金核对/财务对账机制，明确谁、多久核对一次 Agent 发起的退款金额与平台实际扣款
- 上线前先跑“影子模式”：Agent 给出判断但不真正执行，人工核对判断和实际处理是否一致，跑到准确率达标后再放开自动执行权限
- 提前明确出错后的纠错和追责路径，作为放开自动执行权限的前提

## 5. 我们建议 1.0 做成什么样

1.0 需要具备真实自动退款能力，但不做全量自动退款。建议先做「低风险自动退款 + 高风险转人工」。

### 1.0 能力范围

- 根据 SOP 判断处理类型和风险等级
- 对符合 SOP 的低风险场景，自动执行同意退款、确认退款或部分退款
- 对不符合自动退款条件的场景，转人工并说明原因

### 1.0 可优先尝试的自动退款场景

| 场景 | Agent 可以做什么 | 前提 |
|---|---|---|
| 已发货但未揽收退款 | 查询物流，确认未揽收或可拦截后自动同意退款 | SOP 明确未揽收/可拦截可退 |
| 已发货在途退款 | 查询物流和拦截状态，拦截成功后自动退款 | 必须能确认拦截成功或符合平台规则 |
| 退货已签收/验收后退款 | 查询退货物流和验收状态，自动确认退款 | 需要明确签收或仓库验收标准 |
| 小额部分退款 | 按 SOP 金额标准自动发起部分退款 | 少件、破损、差价等金额规则明确 |
| 系统未自动处理的取消/退款单 | 对平台或系统漏掉的低风险单自动处理 | 需要客服确认哪些状态会漏处理 |
| 即将超时的低风险退款单 | 定时扫描待处理退款单，符合规则时自动处理 | 避免超时导致平台自动判责 |

### 1.0 不建议做

- 不自动处理平台介入/纠纷单
- 不自动处理高金额退款
- 不自动处理规则不清晰的部分退款
- 不自动处理已收货仅退款等高争议场景
- 不处理平台/系统已经自动完成的未发货退款
- 不在没有 SOP 和权限边界的店铺直接操作真实退款

## 6. 希望确认的问题

1. 客服是否已有完整退款 SOP？
2. SOP 是否能按平台和处理类型拆分？
3. 哪些退款类型最简单、最稳定、最适合 1.0 先做？
4. 哪些情况必须人工处理？
5. 是否可以提供调研用只读子账号、客服陪跑，以及试运行阶段的受限退款权限？
6. 是否可以提供脱敏历史案例用于规则梳理和测试？
7. 1.0 的自动处理金额上限和权限边界如何设定？
8. 客服主管是否可以指定一位负责人，统一对接 SOP、账号、陪跑和后续确认？
9. 各平台售后处理的强制时效是多少？现在人工处理是否已经出现过因超时被平台自动判责的情况？
10. 售后单的唯一标识是什么？同一交易号是否可能存在多个售后单？
11. 退款“提交成功”和“到账成功”分别如何确认？Agent 处理到哪一步算完成？
12. 审批人如果超时未响应，应该如何处理（自动拒绝、自动升级、还是保持等待）？
13. 使用浏览器 Agent 操作店铺后台，是否符合各平台的商家协议？法务是否评估过这个风险？
14. 如果 Agent 判断错误已经完成退款，现在的补救流程是什么？
15. 用于退款的客服账号，是否会和其他自动化场景（如补发通知 Agent）共用？

## 7. 初步结论

退款 Agent 的第一阶段目标不是覆盖所有退款，而是先把低风险、规则明确、客服重复操作的退款场景自动处理起来。

建议 1.0 从「已发货未揽收/可拦截退款、退货签收/验收后退款、小额部分退款、即将超时的低风险退款」开始，逐步扩展到更复杂的退货退款、部分退款和跨平台退款处理。上线前建议先以“影子模式”验证 Agent 判断准确率，达标后再逐步放开自动执行权限。
