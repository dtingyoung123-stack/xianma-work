01 / START

开始前准备

先确认业务负责人、IT 对接人和最终使用者，减少开发到一半才发现方向不对。

本手册只解决“如何把网站做出来并接入公司环境”。业务规则、数据权限和上线审批仍由部门负责人和 IT 按公司制度确认。

你需要准备的三个人

  • 业务负责人，能确认流程和验收结果。
  • 部门操作人，能提供真实表格、字段和使用场景。
  • IT 对接人，负责数据库、钉钉、服务器、域名和上线资源。

最终要交付什么

  • 一个可在浏览器访问的网站地址。
  • 一份测试数据和操作说明。
  • 一份配置、账号权限、备份和联系人清单。
  • 一份上线验收记录。
02 / SCOPE

先做一个最小可用版本

第一版只完成一条完整业务链路，例如“上传 Excel → 查询 → 导出结果”。

输入用户上传文件、填写表单或选择条件
处理网站校验、计算、调用 AI 或查询数据库
结果页面展示结果，允许下载或继续处理
权限明确谁能看、谁能改、谁能导出

需求描述模板

复制这段内容给 AI，再根据实际情况补充
我需要做一个部门内部网站。
使用部门：【部门名称】
使用人员：【角色和人数】
解决问题：【现在最耗时或容易出错的工作】
输入数据：【Excel / 表单 / 数据库 / 其他】
处理规则：【用业务语言描述】
输出结果：【页面 / 下载文件 / 通知】
必须控制的权限：【谁能查看、编辑、导出】
第一版不做：【明确排除的功能】
请先输出页面流程、数据字段和验收标准，不要直接写代码。
判断第一版是否合格，只看一名新用户能否按照说明独立完成一次真实业务操作。
03 / BUILD

用 AI 创建项目骨架

让 AI 先生成可运行的小项目，再逐步增加功能。每次只修改一个目标。

推荐的第一版目录

department-site/
├─ app/
│  ├─ main.py              # 后端入口
│  ├─ database.py          # 数据库连接
│  ├─ models.py            # 数据表模型
│  └─ routes.py            # 页面和接口
├─ frontend/
│  └─ index.html            # 第一版网页
├─ data/                    # 本地开发数据
├─ .env.example             # 配置示例，不放真实密钥
├─ requirements.txt
└─ README.md

给 AI 的开发提示

要求 AI 先解释修改哪些文件、如何启动、如何验证。每次修改后都要求保留已有功能，并提供最小测试步骤。

每次修改都留下记录

记录日期、需求、修改文件、验证命令和未解决问题。不要把密码、Token、AppSecret 或生产数据库内容发给 AI。

AI 生成的代码必须经过本地运行和业务验收。能生成代码，不等于代码已经安全、正确或可以上线。
04 / ENVIRONMENT

准备开发环境

附件《开发环境检测及安装.txt》要求的重点是“实际能运行”，不是只看软件有没有安装。

以下命令以 Windows PowerShell 为例。电脑已有可用版本时，不要为了追求最新版强制升级。

需要检查的基础工具

工具用途检查命令
Python 3.11+后端、数据处理、机器学习python --version
pip / venv安装依赖和隔离项目环境python -m pip --version
Git保存版本、协作和发布候选git --version
Node.js LTS / npm前端构建和依赖安装node --version
浏览器打开网页和开发者工具打开 Chrome 或 Edge
 
mkdir ai_training_env_check
cd ai_training_env_check
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip

实际导入验证

python -c "import pandas, openpyxl, sklearn, fastapi, uvicorn; print('核心环境 OK')"

开发环境原则

  • Python 依赖安装到项目 `.venv`。
  • Node 依赖写入 `package.json`，不随意全局安装。
  • AI SDK 可以检查 import，不要在没有 API Key 时调用真实模型。
  • 局域网测试服务监听 `0.0.0.0`，并按需开放单个端口。
05 / LOCAL

本地运行和 Smoke Test

在申请生产资源前，先证明网站在本机能完成一条完整链路。

启动 FastAPI

uvicorn app.main:app --host 0.0.0.0 --port 8000

浏览器依次访问 `http://localhost:8000/` 和 `http://localhost:8000/health`。健康检查应返回 `{"status":"ok"}`。

端到端验证链路

  1. 创建或上传一份脱敏 Excel。
  2. 用 Pandas 读取并清洗数据。
  3. 需要时训练模型并执行预测。
  4. 保存、读取并展示结果。
  5. 浏览器访问页面和接口。
  6. 同一局域网设备访问本机 IPv4 地址。
没有真实 API Key 时，报告只能写“SDK 环境正常，真实模型连接待 API Key 验证”，不能写成“AI 已连接成功”。

07 / DINGTALK

接入公司钉钉

钉钉接入分为应用申请、后端认证、账号绑定和联调验收四部分。

申请应用企业内部应用、可见范围、安全域名
后端换身份使用自己的凭证调用钉钉接口
绑定账号用企业和不可变 userid 定位账号
联合验收钉钉客户端、普通浏览器和异常场景
身份关联必须使用正式的 `corpId + dingTalkUserId` 或公司批准的绑定表 ID。姓名、手机号、部门名称只能展示或人工核对，不能作为登录、权限、去重或同步条件。

需要向 IT 提供的信息

  • 网站名称和业务用途。
  • 首页地址、回调地址和安全域名。
  • 使用范围和需要的通讯录权限。
  • 管理员和测试人员的钉钉不可变 ID。

必须保护的信息

  • AppSecret 只配置在后端 Secret 或受控环境变量。
  • 授权码、AccessToken、Cookie 不写日志。
  • 前端不能持有 AppSecret。
  • URL 不携带用户身份、Token 或动态返回地址。

钉钉接入申请模板

应用名称：【网站名称】
应用类型：企业内部应用
首页地址：【待 IT 确认的 HTTPS 地址】
回调地址：【待 IT 确认的 HTTPS 回调地址】
安全域名：【待 IT 填写】
可见范围：【部门 / 成员范围】
通讯录权限：【最小必要权限】
测试账号：【钉钉 userid，不填写姓名代替】

申请服务器和生产资源

生产资源申请要说明网站运行方式、访问对象、端口、备份和联系人。

服务器资源申请模板

项目名称：【网站名称】
运行方式：Docker / 其他【由 IT 确认】
服务器环境：生产
预计访问量：【日访问人数、并发估算】
服务端口：【由 IT 分配】
域名：【申请的正式域名】
数据库：【数据库申请单编号】
文件存储：【是否有上传文件、预计容量】
备份：【数据库、上传文件、配置的备份要求】
访问控制：【内网 / VPN / 互联网 / 钉钉内访问】
监控要求：【健康检查、日志、告警】
上线窗口：【日期和时间】
运维联系人：【部门、姓名、联系方式】

生产配置边界

  • 生产 `.env` 和密钥只存在服务器受控位置。
  • 前端构建时只注入允许公开的非敏感配置。
  • 持久化数据目录单独挂载并纳入备份。
  • 生产数据库不使用本地开发数据覆盖。

部署前输入

  • 代码来源分支和精确候选 SHA。
  • 构建产物和校验值。
  • 生产环境变量清单。
  • 数据库、域名、SSL 和工作台申请结果。
09 / DOMAIN

配置正式域名和 SSL 证书

钉钉回调、浏览器访问和工作台入口都应使用稳定的 HTTPS 地址。

域名申请要写清楚

  • 网站名称和业务用途。
  • 建议域名和备用域名。
  • 是否需要公网访问或仅内网访问。
  • 域名负责人、证书负责人和续期联系人。

SSL 验收内容

  • 浏览器显示证书有效且域名匹配。
  • HTTP 是否按要求跳转 HTTPS。
  • 证书链在钉钉客户端中可验证。
  • 证书到期前有续期负责人。
正式流量通常先经过独立 HTTPS 入口，再由反向代理转发到应用容器或内部端口。应用本身监听的内部端口不等于用户最终访问地址。
10 / DEPLOY

构建和部署生产版本

发布前冻结准确候选，构建、校验、备份、上线和验证都要留下记录。

  1. 开发目录完成代码和定向测试，确认没有未纳入的业务改动。
  2. 从明确来源分支创建干净工作区，记录来源 ref 和 SHA。
  3. 构建前端和后端制品，生成校验值。
  4. 在服务器上核对候选、生产当前版本和备份状态。
  5. 按批准窗口替换或重启对应组件，保留持久化数据和密钥。
  6. 执行首页、健康检查、登录、核心业务、数据库和日志验证。
  7. 记录实际运行版本、域名、验证时间和未解决问题。
docker compose -f src/compose.yaml --env-file .env config --quiet
docker compose -f src/compose.yaml --env-file .env up -d --build
docker compose -f src/compose.yaml ps
docker compose -f src/compose.yaml logs --tail=100
生产部署、数据库结构变更、数据修复、提交推送和环境切换都必须按公司的授权流程执行。本段命令只作为技术示例。
11 / WORKBENCH

接入先马工作台

工作台只维护固定业务编码和固定入口配置，不让前端传入任意跳转地址。

交给 IT 的工作台入口信息

字段填写内容
业务编码【固定编码，例如 DEPARTMENT_SITE】
显示名称【页面展示名称】
业务分类【业务大脑 / 资源库 / 应用】
正式 URL【固定 HTTPS 地址】
钉钉免登入口【已验证的固定入口，例如 /dingtalk-sso】
状态测试完成后由 IT 设置 ENABLED
负责人【业务负责人和 IT 负责人】
工作台入口从门户跳转时，目标系统应在自己的后端完成身份认证、账号绑定、状态和权限校验。门户不传递门户 Cookie、Token、姓名或 AppSecret。

进入工作台前的测试

  • 清除目标系统会话。
  • 在钉钉客户端直接打开固定免登入口。
  • 确认可以建立目标系统自己的会话。
  • 测试未绑定、禁用和无权限账号。

不得直接启用的情况

  • 入口仍是普通登录页。
  • 依赖只能由工作台卡片注入的临时状态。
  • 没有固定 HTTPS 地址或域名未在白名单。
  • 还没有完成业务负责人验收。
12 / ACCEPTANCE

上线验收和交接

上线不是“页面能打开”就结束，而是用户、数据、权限、运维和恢复路径都能说明白。

业务验收

  • 新用户能完成核心流程。
  • 错误输入有明确提示。
  • 结果与人工核对样例一致。
  • 导出文件和页面展示符合业务要求。

技术验收

  • 首页、健康检查和核心接口可用。
  • 数据库连接、备份和恢复方式明确。
  • 日志不泄露密码、Token、授权码和隐私。
  • 证书、域名和钉钉入口在支持的客户端可用。

交接资料

  • 项目仓库和当前运行版本。
  • 配置项清单和密钥保管位置。
  • 数据库表和字段说明。
  • 部署、回滚、备份和联系人说明。

出现问题怎么报 IT

  • 发生时间和访问地址。
  • 操作步骤和实际错误提示。
  • 浏览器、钉钉客户端或服务器日志中的脱敏信息。
  • 影响人数和是否有临时人工方案。

最终交接清单

完成清单后，保留一份“实际版本、实际地址、实际配置状态和实际验收结果”的记录。计划中的地址或测试成功不能代替上线后的真实验证。
